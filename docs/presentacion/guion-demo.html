Guion de demostración (5–7 minutos)

Problema → soberanía → flujo en vivo → ataque bloqueado → caos sin Internet → consola y auditoría → impacto
Equipo PSM-Hackaton · Servicio Soberano de Autenticación Multifactorial basado en Tiempo (TOTP) · 26 de noviembre de 2026
Versión consolidada a partir del guion inicial de Juan Laya (docs/GUION_DEMO.md), con tiempos y comandos verificados el 26-11-2026. Reparto sugerido. Presenta: Enggel Rodríguez. Teclado (portal y app): Javier Rodríguez. Terminal de ataques: Giovani Marcano. Consola: Juan Laya. Respuestas técnicas: Diego Landaeta. Ajustar al equipo el día de la demo.

0. Preparación (antes de subir, 15 minutos)

# Terminal 1 — servicio (instalación limpia, ver README §6)
cd backend
npm run env && npm run certs && npm run seed      # anotar client_id/secret y datos del admin
npm start

# Terminal 2 — Portal de Trámites
cd demo-portal-tramites
cp .env.example .env                               # TOTP_CLIENT_ID / TOTP_CLIENT_SECRET de "Portal de Trámites"
npm run usuarios && npm start

# Terminal 3 — laboratorio (letra grande)
export ATTACK_CLIENT_ID=app_...   ATTACK_CLIENT_SECRET=...     # "Portal de Trámites"
export ATTACK_CLIENT_ID_2=app_... ATTACK_CLIENT_SECRET_2=...   # "Agente Evaluador (Reto 3)"
node attack-lab/ejecutar-todo.js --rapido          # ensayo completo: debe terminar sin fallos
#   (con --comando-arranque "node src/main.js" --pid-backend <PID> incluye el reinicio: 12/12 y 127/127)
  • CA local (backend/certs/ca.crt) importada en el navegador de la demo (README §6.5).
  • App abierta en https://localhost:8443/app/ con PIN creado y la cuenta del administrador añadida (pestaña Pegar).
  • Consola abierta en https://localhost:8443/consola/ con sesión iniciada, en Detector de anomalías. Para entrar: usuario admin_seguridad + contraseña impresa por npm run seed + código actual de la app. Si lo rechaza, esperar al siguiente código: cada código sirve una sola vez (README §6, «Guía rápida de uso»).
  • Recordatorio para el público: el PIN solo abre la app en ese navegador; la consola pide contraseña y código, y el Portal pide cédula, clave y código.
  • Portal en https://localhost:8444, pantalla Ingresar al portal, panel «Lo que ocurre por dentro» visible.
  • Ensayo hecho con V-10.000.001 (Ana); en vivo se usa V-10.000.002 (Bruno) (sin segundo factor). Reserva: E-80.000.003 (Carla). Clave de todos: Tramites-Demo-2026.
  • Informe de la última ejecución abierto en otra pestaña: attack-lab/resultados/informe-<fecha>.html (copia en docs/evidencias/).

1. Guion

0:00–0:45 El problema

«Hoy, cuando un ciudadano entra a un trámite con segundo factor, sus claves suelen vivir en aplicaciones y nubes extranjeras. La institución no controla las semillas, ni la validación, ni los registros. Y muchas de esas apps solo saben SHA-1, aunque el reto exige HMAC-SHA256 y SHA-512.»

0:45–1:30 Soberanía, demostrada

node docs/sbom/generar-sbom.js

Abrir las herramientas del navegador (F12) → pestaña Red en la app y el portal: ninguna petición a dominios externos (ni CDN, ni fuentes, ni analítica).

«Cero dependencias npm, cero librerías externas, cero recursos de terceros: solo los módulos nativos de Node.js. El motor TOTP, el servidor HTTPS, el codificador QR, los JWT y el detector de anomalías son código nuestro, bajo licencia AGPL. El inventario CycloneDX y el hash de cada archivo están en docs/sbom/.»

1:30–3:00 Flujo completo en vivo

  1. Portal: V-10.000.002 (Bruno) / Tramites-Demo-2026 → Continuar. «Primer factor: la contraseña del propio portal.»
  2. Vincule su autenticador → Abrir en el Autenticador Soberano → PIN → Guardar cuenta. «La semilla nació en nuestro servidor con el CSPRNG y se guardó cifrada con AES-256-GCM; viaja una sola vez.»
  3. Escribir el código → Activar segundo factor → mostrar los 10 códigos de recuperación → Continuar al ingreso.
  4. Código nuevo → Verificar y entrar. Señalar en «Lo que ocurre por dentro»: JWT EdDSA, firma comprobada con la JWKS en caché, jti consumido.
  5. Cambio de datos bancarios → pide otro código (step-up) → Confirmar y enviar.
  6. Opcional, si sobra tiempo: en Aplicaciones de la consola, poner la política del Portal en SHA-512 y 8 dígitos y enrolar a E-80.000.003 (Carla): «lo que muchas apps comerciales no calculan».

3:00–4:30 Ataque bloqueado en vivo

node attack-lab/escenarios/replay.js --detallado
node attack-lab/escenarios/jwt.js
node attack-lab/escenarios/spraying.js
«Robamos un código válido y lo reenviamos: rechazado, y con la misma respuesta que un código cualquiera; el atacante ni siquiera sabe que el código era bueno. Diez envíos simultáneos del mismo código: exactamente uno entra.» «Alteramos el token, le ponemos alg: none, lo firmamos con HS256 o con otra clave, lo usamos en otra app o lo reutilizamos: todo rechazado.» «Ahora un atacante prueba pocas veces muchas cuentas para esquivar el bloqueo por cuenta: el detector local, un Isolation Forest programado por nosotros, bloquea el origen; al atacante solo le llega un 429 genérico y las razones las ve el equipo de seguridad en la consola. Todo se calcula en esta máquina.»

Cambiar a la consola → Detector de anomalías → leer en voz alta una razón (por ejemplo, «Una misma IP probó 20 cuentas distintas en 15 minutos»).

4:30–5:20 Caos y sin Internet

  1. Desconectar la red del equipo a la vista del jurado (cable o Wi-Fi; en Linux: nmcli networking off, comprobar con nmcli networking connectivity → none).
  2. Salir del portal y entrar otra vez con V-10.000.002 (Bruno) y un código de la app: «Sin Internet, todo sigue funcionando. La soberanía no se declara: se demuestra.»
  3. Cortes entre el portal y el servicio:
node attack-lab/caos/escenario-caos.js --detallado
«800 ms de latencia: el usuario entra, más lento. Cortamos la red 10 segundos: nadie entra y ningún código incorrecto se aprueba, el sistema falla cerrado. Restauramos: se recupera en milisegundos.»

Reconectar la red al terminar (nmcli networking on).

5:20–6:20 Consola y auditoría

  1. Panel: verificaciones, bloqueos, disponibilidad, latencias y desfase de reloj, sin IP ni nombres.
  2. Aplicaciones → Editar la política del Portal (por ejemplo, SHA-512 u 8 dígitos) y cancelar o guardar.
  3. Llaves de firma → Rotar llave de firma: aparece un kid nuevo y el anterior pasa a solo_verificacion y sigue publicado en /.well-known/jwks.json: «los tokens ya emitidos siguen validando».
  4. Enrolamientos → filtrar por la app «Portal de Trámites» → en el enrolamiento recién creado, Suspender y Reactivar: «un suspendido responde como un código incorrecto; revocar es definitivo». Mencionar que las apps que derivan el user_ref de la cédula con el SDK permiten buscar por cédula sin guardarla, y que desde Administradores se crean cuentas de Operador y Auditor con su propio TOTP.
  5. Auditoría → Verificar integridad de la cadena: «cada evento lleva el hash del anterior; si alguien borra o altera un registro, la cadena se rompe en ese punto».

6:20–7:00 Impacto y viabilidad

«Se despliega en cualquier servidor de la institución con Node.js y systemd, sin contenedores ni Internet, con su propio NTP y su propia CA. Cualquier sistema se integra con nuestro SDK o con cuatro llamadas HTTPS: lo hicimos con el Portal de Trámites y lo ofrecemos al equipo del Reto 3. 340 pruebas automatizadas, 127 verificaciones de ataque y 12 del escaneo dinámico en verde, cero costo de licencias y cero dependencia extranjera.»

Mostrar el informe autocontenido de attack-lab/ejecutar-todo.js y la unidad deploy/servicio-totp.service. Cerrar con la matriz de cumplimiento (docs/cumplimiento/matriz-cumplimiento.pdf) y la escalabilidad (docs/escalabilidad/).

2. Plan B

Si falla…Hacer
El backend no arrancaMostrar cd backend && npm test (237 pruebas en ~7 s) y el informe HTML de docs/evidencias/. Revisar que backend/.env no conserve CHANGE_ME (el servicio lo indica al arrancar).
El portal no conecta con el servicioRevisar TOTP_CLIENT_ID/TOTP_CLIENT_SECRET en demo-portal-tramites/.env. Alternativa sin backend: node ../sdk/testing/servicio-falso.js --puerto 8099 & y TOTP_BASE_URL=http://127.0.0.1:8099 TOTP_CLIENT_SECRET=secreto-de-prueba-no-usar-en-produccion node server.js.
Aviso de certificado en el navegadorImportar backend/certs/ca.crt (README §6.5). No usar la opción de ignorar el aviso delante del jurado.
La cámara no lee el QRUsar Abrir en el Autenticador Soberano o la clave manual (la cámara está permitida en /app/, pero la lectura depende de BarcodeDetector en el navegador).
«Código incorrecto» con el código correctoEsperar al siguiente código (el usado al activar ya no vale); revisar Ajustes → Comprobar hora en la app.
El usuario de la demo quedó bloqueadoLos bloqueos persisten en la base de datos: continuar con E-80.000.003 (Carla).
Un escenario de attack-lab no respondeComprobar ATTACK_CLIENT_ID/SECRET; mostrar la ejecución preparada en el informe HTML; plan B sin backend: cd attack-lab && npm test (28 pruebas, incluido el proxy de caos).
No se puede desconectar la redMostrar solo escenario-caos.js y explicar que el servicio, la app y el portal no hacen ninguna llamada externa (SBOM: 0 recursos externos).
Falta tiempoSaltar la sección de consola y cerrar con la diapositiva de impacto (30 s).

3. Preguntas probables del jurado

PreguntaRespuesta corta
¿Inventaron su propia criptografía?No: RFC 6238, HMAC-SHA256/512, AES-256-GCM, Ed25519 y scrypt, con las primitivas de node:crypto y los vectores oficiales del RFC en las pruebas. Lo propio es la implementación y la custodia.
¿Qué pasa si roban la base de datos?Las semillas y las claves privadas están cifradas con una llave maestra que no está en la base; usuarios e IP solo como HMAC.
¿Y si el servicio se cae?Falla cerrado: nadie entra sin verificar. Un JWT ya emitido se valida sin red con la JWKS en caché. Reinicio medido en 0,33 s.
¿Funciona con otras apps autenticadoras?Sí, el URI otpauth:// es estándar; para apps que solo saben SHA-1 hay modo de compatibilidad por app, desactivado por defecto.
¿Escala?Un proceso con SQLite atiende la demo con p95 de milisegundos; el plan de crecimiento está en docs/escalabilidad/.
